> **CATALOG COST-FIELD FIX — 2026-09-25, build `et`:** Found a real field-level bug the 2026-09-05 audit missed (it verified catalog *record* create/edit/delete, not the cost field specifically). The catalog cloud sync speaks `default_cost` / `default_hours`, but the entire catalog UI — render (`renderCatalog`), Price Update Mode, `saveCatalogItem`, and the quote/invoice/work-tracking readers — speaks `mc` (material cost) / `lh` (labor hours). The two never met: the **pull** (auth.js) wrote `cost`/`hours` (which nothing reads) so cloud costs rendered **$0.00**, and the **push** read `item.cost` (always undefined for UI-created items, whose real field is `mc`) so every UI-entered catalog cost was written to the cloud as **0**. Fixed both mappings in `auth.js` (build `et`): pull now sets `mc`/`lh` (keeps `cost`/`hours` too, harmless), push now reads `item.mc`/`item.lh` with fallback to `cost`/`hours`. **Live-verified 2026-09-25 on the deployed build `et` (as the real signed-in user): 319 catalog cards render correct costs matching the DB exactly (e.g. 1 INCH CLIP CABLE J-HOOK $2.77, 1-Year Camera License $142.35, 19 IN. 6 OUTLET POWER STRIP $79.00); inventory intact at 327; no console errors.** This is the mechanism behind any recurring "catalog costs are blank on a fresh device / disappear when I come back" reports. **No cost data was lost in the 2026-09-25 PriceBook import** — proven by the pre-import daily snapshot (`tcss_backup_daily`, 2026-09-24 23:08) which shows the 116 pre-existing catalog items already had **zero** material costs (`mc`=0 and `cost`=0 for all), and the 327 imported items now carry correct `default_cost` in the cloud (sum **$27,469.50**, 319 with a cost). Quantities were intentionally not imported (qty=0). **Duplicate cleanup DONE + live-verified 2026-09-25:** the original catalog was 58 unique items each entered twice (116 rows, all $0 cost, identical description/category/unit/notes — a seed set loaded twice; the import added zero name-collisions). The 58 exact-duplicate copies were soft-deleted (kept one per pair; `is_active=false`, tagged `import_batch='dedup-removed-2026-09-25'`), full backup taken (`_bk_catalog_dedup_20260925`). Catalog is now **385 active** (58 originals + 327 imported), **0 duplicate groups**, costs intact (319 priced) — verified live in-app after Joe re-signed-in (a mid-task Supabase session expiry had temporarily made the client read 0 rows; a reload+login healed it, and the wholesale-replace-on-pull means the removed rows can't resurrect). Reversible: restore from the backup or by flipping `is_active` back on the tagged rows.

## 🟡→🟢 Numbering counters — RESOLVED (as + migration _17) — LIVE-VERIFIED

Previously the quote/job/WO/PO/invoice numbers were minted per-device from local counters that never synced (five paths blind-incremented without reconciling), so two devices could collide or a fresh device could re-issue an existing number — and creating an inventory item silently shifted invoice numbers (shared `DB.invSeq`). **Fixed:** an atomic `next_number()` RPC + `number_sequences` table (migration _17) now allocate every business number server-side; asset tags got their own self-healing allocation. Verified as a real user on build `as`: created a quote (**Q-2049**), work order (**WO-1006**), invoice (**INV-1001**), and PO (**PO-1003**) — each server-allocated, sequential, and its counter advanced by exactly one — and an inventory item's tag no longer moves the invoice counter. (Job `J-` + the auto-WO on quote→job conversion use the same proven `allocNumber` helper; verified by construction.)

## 🟡 YELLOW — caveats (lower priority, not data-loss) — still open

- **Blob-synced groups** (tools, tool checkouts, checkout log, inventory locations, inventory transfers, time-off requests, absences, and the payroll/tool side-records from RED #7) sync the whole list at once, so two people editing different rows at the exact same moment can overwrite each other (last-save-wins). Fine for a small crew; per-row is the robust upgrade.
- **Write-but-not-read-back**: WO field logs, tech journal, and raw clock sessions/events are written to the cloud but only read on-demand or for live status — so the read side is effectively per-device. (The durable payroll records — time entries + work-days — DO sync.)
- **No working delete** for: WO documents, job photos, vendors (no vendor-delete exists at all). WT check-off / assignment deletes are unguarded (low risk; check-offs self-heal).
- **Offline numbering**: when a device is offline, numbering falls back to a self-healing local increment; two devices both offline could briefly pick the same number until they sync (the server floor then advances everyone). Online allocation is fully atomic.

## Sync performance (2026-09-19, builds `cs` → `cx`)

**Symptom:** after the Phase-2 CRM history import, a hard refresh froze the app ~45s and every save/sync froze ~14s; users complaining. **Outcome:** fixed and verified live.

**Diagnosis (measured live in the app + Supabase MCP — NOT guessed; this replaced three earlier guess-patches):** two distinct problems. (a) The initial post-login sync showed a **blocking** overlay and several history tables were pulled **in full** every sync — `wo_expenses` 8,281 rows, `purchase_orders` 1,488 + `po_line_items` 7,082. (b) The far bigger one: **`saveDB` LZString-compressed the entire 10.86MB in-memory DB synchronously on the main thread — ~14s freeze — firing on every save, on the pre-sync restore point, and at end of every sync.** Opening a work order was only 83ms; the freeze was always the *save*. Import preserved real historical `created_at` (2015–2026), so date-window bounding is safe.

**Build `cs` — stop blocking the UI.** `syncAllFromCloud` runs silently/in-background whenever a local cache already exists (every hard refresh). No data-logic change. 45s → ~15s.

**Build `ct` — load-on-demand for the two big tables** (cuts ~13,800 rows/sync). `wo_expenses`: pull last 365 days (8,281 → 1,809); a WO's full set fetched on `openWorkOrder`/`createWOInvoice`, a vehicle's on profile open. `purchase_orders`: recent 365d + all still-open POs; older closed POs via `ensurePOLoaded`. Shared `_mapPORow`. PO numbering already server-side so bounding is safe.

**Build `cu` — PO status correctness.** Switched from a native-status allow-list to a **closed-list exclusion** (`PO_CLOSED_STATUSES`) because imported POs use legacy CRM status strings (`Completed`, `Open`, `All Received -- Open`, `Partially Back Ordered`…). Working set 1,488 → 130, including all 19 open POs of any age.

**Build `cv` — nav lag + import placeholder.** Made per-open expense fetch lazy (Expenses tab / invoice / debounced header) so stepping WOs is instant; fixed `woRtfLoad` so programmatically-loaded Internal Notes no longer render the placeholder on top ("double writing" on imports). Both verified live.

**Build `cx` — off-main-thread compression (the big one).** The ~14s synchronous LZString compress now runs in a **Web Worker** (new `js/lzstring.js`, imported by the worker). `saveDB` is debounced; `_saveRestorePoint`, `_saveDailySnapshot`, and the two end-of-sync persists in `auth.js` all use the async packer. If the worker is unavailable it falls back to the synchronous pack, so worst case = prior behavior. `loadDB` (decompress ~2s) unchanged; storage format + cross-tab `storage` event unchanged.
- **Verified live on the DEPLOYED build (`core.js?v=20260919cx`), with the real 10.86MB DB:** `_dbPackAsync` main-thread block **~200–300ms** (was ~14,000ms), worker active (`worker_alive:true`, not the fallback), packed cache unpacks back to the exact 500 work orders (integrity OK), `saveDB()` runs without error, no console errors. The ~10s compress happens off-thread and is invisible to the user.

**Still open (optional, not a freeze anymore):** compression still *runs* (~10s) but off the main thread, and the localStorage ~5MB ceiling still exists (compressed cache ~2.3MB today, headroom fine). Moving the local cache to **IndexedDB (uncompressed, async)** would remove compression entirely and lift the size cap — a bigger, deliberate change for later, not needed to resolve the freeze.
